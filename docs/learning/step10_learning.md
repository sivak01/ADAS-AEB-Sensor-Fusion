# Step 10 — learning note

## The idea in plain language (≤ 8 sentences)
This step builds the actual scorecard — the thing that turns a pile of "the system said X, the truth was Y" comparisons into honest numbers a person can judge the whole project by. It scores the way a real braking-system engineer would: at each real moment something was in the vehicle's path, did the system react correctly, brake too little, too much, not at all, or raise a false alarm when nothing was actually there? Every rate is reported with the raw count it came from and a confidence interval, because a rate with no denominator attached is a number without context — "100% correct" means something very different built on 2 examples versus 200. A sensor is never blamed for missing an object it could never have physically seen, so every single-sensor result is computed twice: once counting every real danger, and once counting only the dangers that sensor could plausibly have detected. And to prevent the single most common way an evaluation quietly lies to itself — tuning and testing on the same data — this step includes a hard, code-level lock that refuses to score the held-out test scenes at all unless the configuration has been explicitly frozen and marked final.

## Tiny worked numeric example
Two different runs both report a "false-brake rate" of exactly 20%. Run A got there from 1 false brake out of 5 opportunities; Run B got there from 20 false brakes out of 100. Reported as a bare percentage, they look identical. Reported the way this step requires — with raw counts and a 95% confidence interval — Run A's real range is roughly 4% to 62% (genuinely could be anywhere from "basically never" to "quite often"), while Run B's is a tight 13% to 29%. The two "20%" numbers are not remotely equivalent claims, and only the second one is solid enough to draw a real conclusion from — which is exactly why this step refuses to let a rate be reported as a bare number, ever.

## Why it is designed this way (which past mistake it prevents — cite what-not-to-do.md section)
This step is a direct, comprehensive build-out of what-not-to-do.md §7's tuning-honesty rules and §6's evaluation-honesty rules together. "Don't tune anything to make fusion look better than it measures" and "don't tune debounce thresholds or danger-zone cutoffs on the same scenes you'll report evaluation numbers on" become a real, enforced mechanism here — not just a promise, a piece of code that actively refuses to run without the right flag and the right frozen configuration hash, with every attempt (including refused ones) logged for a permanent record. "Don't score a sensor's blind spot as a tracking failure" (§6) becomes the two observability-aware variants computed for every single-sensor run. And "don't treat a small number of danger events in nuScenes-mini as statistically solid" (§7) is why every rate carries both a raw count and a confidence interval, and why anything built on fewer than a chosen minimum count gets explicitly labelled "indicative only" rather than presented with false confidence.

## How to explain this in an interview (3 bullets)
- "I built a hard, code-enforced guard around the held-out test data, not just a documented policy — scoring the evaluation scenes requires an explicit 'final' flag and a matching cryptographic hash of the frozen configuration, and every attempt to score them, successful or refused, gets permanently logged. This turns 'don't peek at the test set' from a rule people have to remember into something the code itself refuses to violate."
- "Every rate I report comes with both its raw count and a proper statistical confidence interval, computed with a well-known method (the Wilson score interval, which I validated against two published reference values before trusting my own implementation) rather than the simpler, more naive approximation that behaves badly on small samples — which matters a lot here, since some of these denominators are genuinely small."
- "I made sure a sensor's own physical blind spots can never be mistaken for a tracking failure, by scoring every single-sensor result twice: once against every real danger, and once against only the dangers that sensor could plausibly have detected at all, using the dataset's own point-count and visibility data."

## Common misunderstandings
- **"A 95% confidence interval means we're 95% sure the true rate is in that range."** It's a subtler statement than that — it means the *method itself* would contain the true value 95% of the time if repeated many times, not that this one specific interval has a 95% chance of being right. The practical takeaway that matters here is simpler: a wide interval means "don't trust this number much yet," which is the whole reason for computing it.
- **"If fused wins on the unrestricted GT comparison but loses on the observable-restricted one (or vice versa), one of the two numbers must be wrong."** Both can be simultaneously true and both meaningful — they're answering two different, both-legitimate questions: "how good is the whole system, including its blind spots" versus "how good is the system at the things it could physically have seen."
- **"The split guard is basically a formality once you already know you're supposed to use the tuning split."** The whole point is that it doesn't rely on anyone remembering — it's a hard failure with no override except the specific frozen-hash match, precisely because "I meant to only use the tuning split" has been the actual cause of dishonest-looking results in real projects before.
