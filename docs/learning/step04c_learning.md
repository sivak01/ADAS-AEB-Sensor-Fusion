# Step 04c — learning note

## The idea in plain language (≤ 8 sentences)
A camera gives you a flat, 2D rectangle around an object in an image — it never directly tells you how far away that object is, because a photograph throws depth information away by design. To recover distance from a single camera, you need some extra assumption to fill that gap, and this project uses the simplest physically grounded one: assume the road is flat, then trace a straight line from the camera through the bottom of the detected box (where the object touches the ground) until that line hits the ground plane — wherever it lands is the object's distance. This works, but it's inherently fragile in a way LiDAR and radar aren't: a tiny one-pixel wobble in exactly where a box's bottom edge sits translates into a small position error nearby, but a *huge* one far away, because the viewing angle to a distant object is so shallow that a sliver of pixel uncertainty covers many metres of real ground. Getting a genuinely camera-only distance is also surprisingly easy to fake by accident — the most tempting shortcut is to quietly borrow a nearby LiDAR point's real depth and call the result "camera," which defeats the entire point of measuring what a camera can do on its own. This step is built around making that shortcut structurally impossible, not just something a person remembers not to do.

## Tiny worked numeric example
A pedestrian's box bottom sits at pixel row 700 in a 900-pixel-tall image, with the camera 1.5m off the ground and a focal length of 1000 pixels; ground-plane geometry places them at roughly 6 metres away. Now suppose the detector's box bottom is off by just 2 pixels (a tiny, realistic detection wobble) — at that close range, the recovered distance shifts by only a few centimetres, barely noticeable. Take the *same* 2-pixel wobble on a pedestrian who is genuinely 60 metres away, where their box bottom sits just a few pixels above the horizon line: that same tiny 2-pixel error can now shift the estimated distance by **many metres** — sometimes wildly, if the box bottom happens to sit close enough to the horizon that the math becomes numerically unstable (division by a near-zero number). This is exactly why this step's own real-data check found error growing from under 2 metres close up to over 17 metres beyond 50 metres — not a bug, but the direct, measured consequence of this geometry.

## Why it is designed this way (which past mistake it prevents — cite the predecessor project's own lesson)
The predecessor project (V1) built two different camera pipelines and reported both as if they answered the same question. One of them — the one actually labeled "camera" in its results table — quietly looked up the nearest real LiDAR point inside each 2D box and used *that* point's real, LiDAR-measured depth as the detection's position. The camera contributed a box and a class label; a completely different sensor secretly supplied the one number (distance) that the whole comparison was supposed to be testing. V1 built a second, genuinely LiDAR-free pipeline later specifically to correct this, but only after the first version had already been silently comparing "camera" against LiDAR and radar as if it were a fair fight. This step's isolation test exists precisely because a mistake like that is very easy to reintroduce by accident — a single stray import, or one convenient shortcut during a rushed fix, could silently let real depth data leak back in, and nobody reviewing the final numbers would necessarily notice, since a LiDAR-assisted "camera" result simply looks *better* than a real one, not obviously wrong.

## How to explain this in an interview (3 bullets)
- "I built a genuinely single-sensor camera pipeline using ground-plane back-projection — tracing a ray from the camera through a detection box's bottom-centre pixel down to an assumed flat ground plane — rather than any learned depth model, and I made the failure mode of that assumption (error growing sharply with distance) an explicit, measured, reported number rather than a hidden weakness."
- "I wrote a structural isolation test — not just a code review checklist — that statically scans the camera module's own source and imports for any reference to the other sensors' loaders or channel names, and separately runs the real adapter with a data loader that raises an exception on any non-camera file access. This makes a specific, documented mistake from an earlier version of this project (secretly borrowing another sensor's depth) impossible to reintroduce without the test suite catching it immediately."
- "When I found the camera-only system missed every real danger event in my test set, I didn't stop at the headline number — I traced it back to the exact frames involved and found two distinct, real causes: the 2D detector simply missing the object in some frames, and depth noise occasionally pushing a real, visible object's estimated position just outside the vehicle's driving corridor. That's a materially different, more honest story than a single 'camera doesn't work' conclusion."

## Common misunderstandings
- **"If depth error grows with range, the whole approach is broken."** It's a real, serious limitation, but a bounded and well-understood one — it means treating camera-only distance as trustworthy mainly at short-to-medium range, and is exactly why this step measures and reports the error curve explicitly rather than either hiding it or treating every camera detection as equally reliable regardless of distance.
- **"A sensor being labeled 'observable' (GT says the object was visible) but the system still missing it must mean the code is wrong."** Not necessarily — "visible enough to be labeled by a human annotator looking at the full image" is a much easier bar to clear than "detected by an automated 2D detector, in this exact frame, with a depth estimate accurate enough to land inside a tight driving corridor." Both can be true at once without either being a defect.
- **"An isolation test is just extra paperwork if you already know not to mix in other sensors' data."** The predecessor project's own history says otherwise — the person who wrote V1's "camera" baseline almost certainly wasn't trying to cheat; a convenient depth source was reached for during development and it was never revisited before the number was reported as a real single-sensor result. A test that catches this automatically doesn't rely on anyone remembering to check.
