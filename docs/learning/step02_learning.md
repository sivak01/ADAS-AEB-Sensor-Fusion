# Step 02 — learning note

## The idea in plain language (≤ 8 sentences)
Every sensor on the car reports positions relative to itself — a LiDAR point is "3 metres in front of the LiDAR," not "at this spot on Earth." To compare a detection now against a detection half a second ago, or a LiDAR point against a radar point, everything first has to land in one shared frame: the global (world) frame. Getting there is a two-step chain — sensor frame → ego (vehicle) frame, using the sensor's fixed mounting calibration, then ego frame → global frame, using the vehicle's own pose at that exact instant. The critical, easy-to-get-wrong part is that "that exact instant" is different for every sensor: LiDAR, each radar, and each camera all fire at their own real timestamps, with their own recorded vehicle pose, even within one nuScenes "sample." Mixing up whose pose belongs to which reading is the single most common bug class in this kind of pipeline. This step builds that transform chain once, as a tested utility, so every later adapter uses the same correct math instead of five slightly-different copies.

## Tiny worked numeric example
Ego vehicle at global position (10, 5), facing 90° (yawed left from the x-axis). A sensor point sits at (1, 0) in the ego's own frame — "1 metre straight ahead of the vehicle." Rotating that point by the vehicle's 90° heading turns "1 metre ahead" into "1 metre in the +y direction" (since facing 90° means the vehicle's "forward" now points along global +y), giving a rotated offset of (0, 1). Add the vehicle's own global position: (10 + 0, 5 + 1) = (10, 6). That's the point's true global-frame position — and note it's not just "add the translation" (which would wrongly give (11, 5)); the rotation has to happen first, or "ahead of the car" gets pointed in the wrong global direction the moment the car isn't facing along the x-axis.

## Why it is designed this way (which past mistake it prevents — cite what-not-to-do.md section)
This targets what-not-to-do.md §2 directly: "Don't reuse one channel's `ego_pose` for another channel." Two bugs were previously found and fixed from exactly this mistake — reusing LIDAR_TOP's timestamp/pose for radar. `FrameContext.from_event()` makes that bug structurally impossible rather than relying on discipline: it only ever accepts a specific event's own `calibrated_sensor_token`/`ego_pose_token`, with no `channel=` parameter anywhere that could let a caller (accidentally or otherwise) borrow a different channel's pose. what-not-to-do.md §5 is also directly relevant here in a way this step's own investigation surfaced unexpectedly: "don't trust a sensor's own reported values without checking" turned out to apply to a *ground-truth attribute label*, too — a real nuScenes-mini instance carries `vehicle.parked` on every one of its annotations while visibly moving ~5.4 m/s according to its own recorded position. The fix wasn't to loosen the test's tolerance; it was to stop trusting the label and check the GT box's own position directly.

## How to explain this in an interview (3 bullets)
- "I validated the transform two independent ways on real data, not just a hand-derived example: against the dataset's own ground-truth position (floating-point-exact agreement) and against a parked vehicle's LiDAR points, which should — and did — land in nearly the same global spot from two different vehicle viewpoints."
- "When a validation test failed with a 2-metre discrepancy, I didn't loosen the tolerance — I cross-checked the transform against ground truth first, confirmed the code was correct, and traced the actual cause to a mislabeled 'parked' vehicle in the dataset that was really moving, then fixed the test's own selection logic to verify stationarity independently rather than trusting the attribute."
- "I deliberately built the coordinate transform against the official nuScenes devkit's own function rather than re-deriving quaternion math by hand — even though a hand-rolled version in an earlier iteration of this project looked mathematically correct, using the tested library implementation removes an entire class of convention/version bugs for free."

## Common misunderstandings
- **"If two sensors are in the same nuScenes 'sample,' they were captured at the same instant."** Not true — a `sample` groups roughly-synchronized keyframes, but `sample_data` timestamps for different channels within one sample can differ by tens of milliseconds (measured here: up to ~40 ms for CAM_FRONT vs. LIDAR_TOP), during which the vehicle has already moved.
- **"A correct-looking hand-rolled transform is just as good as the library's."** Even a mathematically sound reimplementation (as V1's `src/geometry.py` turned out to be, on inspection) is worth avoiding when a tested, versioned devkit function exists — the risk isn't usually "is the math right," it's silent convention drift (quaternion order, rotation direction) across devkit versions that a hand-rolled copy won't automatically track.
- **"A test tolerance failure means loosen the tolerance."** The opposite instinct is correct: a failing assertion is a prompt to find the actual cause (here: a mislabeled GT attribute), not evidence that the assertion was too strict.
