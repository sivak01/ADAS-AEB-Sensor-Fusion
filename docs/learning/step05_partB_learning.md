# Step 05 Part B — learning note

## The idea in plain language (≤ 8 sentences)
Part A could only ask "is this object here, right now" using a wide, generous position-only test, because at detection time nothing has a velocity yet. Once a track has survived long enough to get a real velocity estimate, a much sharper question becomes possible: not just "is it here," but "is it clearly about to be here" — a car drifting in from the shoulder, or crossing into the lane ahead. Answering that needs the object's motion *relative to the ego vehicle*, not its raw speed over the ground, because what matters is whether the gap between the two of them is actually closing, exactly the same relative-motion idea TTC itself depends on. This step projects a track's current relative velocity forward by a short, fixed time window and asks whether that projected position would fall inside the true, tight corridor — while never trusting a velocity that isn't reliable yet, falling back to Part A's cruder position-only test instead when that happens.

## Tiny worked numeric example
An object sits 3 meters to the side of the corridor's edge (corridor half-width 1.2 m), moving at 2 m/s sideways toward the ego's path while also closing the forward gap. Projected forward by this project's 1.5-second horizon, that lateral drift covers 2 × 1.5 = 3 meters — enough to cross the full 3-meter gap and land exactly on the corridor's centerline. Compare that to a parked car sitting at the same 3-meter lateral offset with zero velocity: even though the ego is closing the *forward* distance to it just by driving past, the car's lateral position never changes, so the same 1.5-second projection still places it 3 meters outside the corridor — correctly excluded, because only one of the two distances (lateral, not longitudinal) determines whether an object actually enters the path.

## Why it is designed this way (which past mistake it prevents — cite what-not-to-do.md section)
This directly extends what-not-to-do.md §5's closing-speed discipline ("closing speed is the RELATIVE motion toward the ego vehicle... skipping the ego-velocity term silently reports high closing speed for two vehicles simply traveling together at the same speed") into the geometric domain: relative velocity, never a track's raw absolute velocity, is what decides whether it's "entering." The design contract's own instruction that a position-only filter "must be generous" is what the eligibility fallback protects — rather than either wrongly promising a confident ENTERING verdict from an untrustworthy velocity, or wrongly discarding a track just because its velocity isn't proven yet, the design explicitly falls back to the wider, safer Part A test and *labels* the result as provisional, so nothing downstream mistakes an uncertain guess for a confident one.

## How to explain this in an interview (3 bullets)
- "I split 'is this relevant' into two different tests running at two different points in a track's life, on purpose — a generous position-only filter the instant a detection arrives (no velocity exists yet), and a stricter, motion-aware test once a track has proven itself with real updates — rather than trying to force one test to do both jobs well."
- "I caught a subtle correctness issue before it became a bug: a naive version of the 'approaching' check that only looked at the closing distance would have misclassified every stationary roadside object the ego vehicle drives past as 'entering the path' — because the distance genuinely is closing, even though the object never moves toward the corridor at all. Testing the full extrapolated position, not just one axis, fixed it before it shipped."
- "I explicitly labeled results built on an untrustworthy velocity as 'provisional' rather than letting the system report a false confident answer — that distinction (a system that says 'I don't know for sure' versus one that guesses and hides the guess) is a real safety-relevant design choice, not just an implementation detail."

## Common misunderstandings
- **"A stationary object should never be flagged as approaching, since it isn't moving."** From the ego's own point of view, it functionally *is* moving — relative velocity is what matters, and a parked car's relative velocity toward an oncoming ego vehicle is very much nonzero. What correctly keeps it excluded is that its *lateral* position never changes, not that its motion is somehow ignored.
- **"Rotating a velocity vector between frames works the same way as rotating a position."** It doesn't — a position transform includes both rotation and translation (where the frame's origin itself has moved to), but a velocity is a direction-and-magnitude only, and translating it would be physically meaningless. Reusing position-transform code for a velocity is an easy, subtle mistake.
- **"If eligibility fails, the track should just be treated as 'not relevant' and dropped."** The design instead falls back to a *different*, cruder test (Part A's generous gate) and marks the answer as uncertain — silently dropping a track just because its velocity isn't trustworthy yet would risk missing something that's actually about to matter.
