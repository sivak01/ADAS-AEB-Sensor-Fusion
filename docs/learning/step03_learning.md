# Step 03 — learning note

## The idea in plain language (≤ 8 sentences)
A Kalman filter keeps two numbers alive at once: its best guess of where something is and how fast it's moving (`x`), and how *unsure* it is about that guess (`P`, a covariance matrix). Every time a bit of time passes with no new measurement, `predict()` moves the guess forward using the last known velocity and makes the uncertainty grow — the longer since the last real look, the less you should trust the guess. Every time a real measurement arrives, `update()` blends the prediction with that measurement, weighted by how much you trust each: a noisy sensor (`R` large) barely moves the estimate; a precise one snaps to it. `Q` (process noise) and `R` (measurement noise) are the two "trust knobs" — `Q` says how much the *thing itself* might be accelerating/turning unpredictably, `R` says how noisy *this particular sensor reading* is. This project uses exactly one Kalman filter design for two different jobs: tracking external objects (later, step06) and tracking the ego vehicle's own velocity (this step) — because raw GPS-style position data has no velocity field built in, so velocity has to be *derived*, and it should be derived the same careful way every time, not by a shortcut.

## Tiny worked numeric example
Two position readings, 0.05 s apart, each with 5 cm of measurement noise: reading 1 at x=0.000 m, reading 2 at x=0.100 m (but the true motion might really be anywhere between, say, 0.075 m and 0.125 m of true displacement, because each reading itself could be off by up to ~5 cm). A raw two-point finite difference computes velocity as (0.100 − 0.000) / 0.05 = **2.0 m/s** — treating the two readings as if they were exact. But the real uncertainty in that displacement is roughly √(0.05² + 0.05²) ≈ 0.07 m, which over 0.05 s is **±1.4 m/s** of pure noise riding on top of the "2.0 m/s" answer — the naive calculation has no way to know or report this, and every subsequent naive velocity estimate inherits the same blown-up noise. A Kalman filter instead keeps a running belief about velocity and only nudges it by however much the new measurement actually disagrees with the prediction, scaled by how trustworthy that measurement is — so a single noisy pair of points can't single-handedly produce a wild 2.0 m/s (or worse) spike the way a raw finite difference can.

## Why it is designed this way (which past mistake it prevents — cite what-not-to-do.md section)
This step directly targets what-not-to-do.md §3: "Never compute an object's velocity, or the ego vehicle's own velocity, as `(pos2 − pos1) / dt`... this exact shortcut was found and fixed independently in four different places in V1/V2." Ego velocity is explicitly named as needing the same discipline, precisely because `ego_pose` has no velocity field and it would be easy to reach for the shortcut "just difference two poses." The Joseph-form covariance update (rather than the simpler textbook form the predecessor project used) targets a subtler, forward-looking version of what-not-to-do.md §4's gating concerns: a covariance matrix that accumulates tiny numerical errors over many predict/update cycles can silently stop being a valid covariance (lose positive-semi-definiteness), which would corrupt every downstream Mahalanobis-gate decision — Joseph form is the standard defense against that failure mode.

## How to explain this in an interview (3 bullets)
- "I validated the filter's self-consistency with a Monte-Carlo NEES test, not just unit tests that check individual behaviors — averaged over 300 runs, the normalized estimation error squared came out to 3.96 against a theoretical ideal of 4.0 (the state dimension), which is strong evidence the process-noise and measurement-noise models are correctly implemented relative to each other, not just individually plausible."
- "When a real-data test failed with a tiny negative time delta, I didn't add a try/except to swallow it — I traced it to floating-point drift in an accumulated-float internal clock, and fixed the actual representation (switched to exact integer microseconds, matching the rest of the codebase's timestamp convention) rather than just widening a tolerance."
- "I found and fixed a real performance problem before it could become a hidden bottleneck later: an early version of the ego-state estimator rebuilt its entire Kalman filter chain from scratch on every query, which is fine for a handful of calls but became a multi-minute stall once tested at realistic native-rate query volume — I replaced it with an incremental cache that only processes new data since the last call, while explicitly keeping a slower-but-correct fallback path for the rare backward-in-time query."

## Common misunderstandings
- **"A Kalman filter needs the actual noise value to be exactly right, or it's useless."** Not quite — the NEES test specifically checks whether the filter's own *belief* about its uncertainty (`P`) matches its *actual* error, not whether the true real-world noise matches some assumed constant exactly. A filter can be "wrong" about the true physical noise and still be well-calibrated if `Q`/`R` are self-consistent with how the filter is actually used.
- **"`predict(dt)` and the filter's own sense of 'current time' are the same thing."** They're related but distinct here: the public `predict()` method only ever takes a time *delta*, by design (per this step's spec) — but the class still needs an internal notion of absolute time to support peeking forward to an arbitrary future instant (`state_at()`) without that peek permanently advancing the filter's real state.
- **"Because a scene 'resets' the ego-state estimator, that's the same rule as 'no scene-boundary reset for tracks.'"** These are two different rules serving two different purposes: resetting ego state per scene is about not treating two unrelated driving-log segments as one continuous trajectory (a data-boundary fact); the tracker's "no scene-boundary reset as its own subsystem" rule (G11) is about not building extra bookkeeping for a scenario that mostly can't happen anyway, since tracks are short-lived by design. They happen to both involve the word "scene," but for unrelated reasons.
