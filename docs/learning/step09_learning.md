# Step 09 — learning note

## The idea in plain language (≤ 8 sentences)
The tracking system updates itself constantly — 10, 13, even 20 times a second, whenever a sensor reports something new. The ground truth this project checks itself against, though, only exists at fixed moments about twice a second, since that's how often the dataset's human annotators actually labeled the world. To fairly ask "did the system get this right," you have to ask what the system believed at exactly that annotated instant — not just grab whichever update happened to be nearby, since "nearby" could still be a tenth of a second off, and a fast-moving car covers real distance in a tenth of a second. This step answers that by taking a track's most recent real update *before* the ground-truth instant and projecting it forward using its own known velocity — but only within a strict, honest limit: never further than the point at which the track would already have been considered dead, and never backward to a time before the track existed in the first place.

## Tiny worked numeric example
A track's last real update puts an object at x=10m, moving at 5 m/s, timestamped at t=1.000s. The ground-truth instant to compare against is t=1.200s — 0.2 seconds later, well within this project's short eviction window (0.3s). The projected position is 10 + 5×0.2 = 11.0m — and that's exactly what this step's own test confirms, matching the extrapolation formula analytically to six decimal places. Now imagine the ground-truth instant were instead t=1.500s — half a second later, beyond the 0.3-second cutoff. Rather than stretching that same track another 0.5 seconds forward and presenting a confident-looking answer, the system correctly reports "STALE" — because a real system would already have considered that track lost by then, and pretending otherwise would be comparing against a fiction.

## Why it is designed this way (which past mistake it prevents — cite what-not-to-do.md section)
This step is a direct, named fix for two specific, previously-confirmed bugs: what-not-to-do.md §6 states plainly, "don't extrapolate without bounds" and "never extrapolate backward before a track's first real snapshot," both explicitly called out as "real bugs found in V2, not hypothetical edge cases." Reading the actual, already-fixed version of the old project's code confirmed both guards exist there with exactly this reasoning — which meant this step could reuse the *reasoning* directly rather than rediscovering it from scratch. One thing worth carrying forward more carefully than the old version did: the old project's extrapolation used simple arithmetic and never grew its own uncertainty estimate over the extrapolation gap, because it never needed to — it only ever compared raw position. This project's eligibility rule depends on that uncertainty growing over time, so reusing the *actual, already-tested* prediction machinery (rather than writing a second, simpler copy of the same formula) was a deliberate choice to avoid two silently-diverging implementations of "predict forward" existing in the same codebase.

## How to explain this in an interview (3 bullets)
- "I didn't rediscover the extrapolation-bounds problem from scratch — I read the earlier project's own, already-fixed code first, confirmed the exact reasoning behind both guards, and reused that reasoning directly, while deliberately not reusing the specific numeric constant it used, since this project's tracks are intentionally much shorter-lived by design."
- "When I needed to predict a track's state forward to an arbitrary future instant, I reused the exact same, already-tested prediction method the live tracker itself uses internally for gating, rather than writing a second, simpler version of the same math — even though the simpler version would have been slightly less code, because two independent implementations of the same idea are two places for them to quietly drift apart."
- "I explicitly did not reuse the earlier project's 'locked identity' approach to matching tracked objects against ground truth, even though it would have been the more familiar, ready-made pattern to copy — because it's a scene-long-identity concept this project's entire design deliberately avoids, and copying it here would have quietly reintroduced exactly the kind of complexity the whole rescope exists to remove."

## Common misunderstandings
- **"Extrapolating forward from the nearest update is always more honest than picking a stale one."** Not without a bound — extrapolating arbitrarily far forward just replaces one dishonesty (using stale data) with another (inventing data for a period the system would have already given up on).
- **"A quick manual formula and a 'properly modeled' prediction give the same answer, so it doesn't matter which one is used."** For the raw position, that's true here — but this step specifically needed the uncertainty estimate to grow correctly over the extrapolation gap too, which the manual formula alone doesn't provide.
- **"Matching a live system's tracks to ground truth is the main way this project measures correctness."** It isn't — the step file says so explicitly: this diagnostic association exists only to explain *which* real object a false alarm was about, for debugging purposes. The actual scoring (coming in step10) doesn't depend on it at all.
