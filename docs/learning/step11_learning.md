# Step 11 — learning note

## The idea in plain language (≤ 8 sentences)
Every earlier step in this project built one piece of a real-time collision-warning system and proved that piece works in isolation; this step is where all four sensor configurations — LiDAR alone, radar alone, camera alone, and all three fused together — finally run through the exact same pipeline and get compared honestly, on data that was never looked at during any of the tuning. The single most important idea here is the *control experiment*: you cannot claim "fusion is better" unless you also measure what each individual sensor achieves on its own, using identical code and identical shared settings, so the only thing that differs between the four numbers is genuinely the sensors involved. A small number of shared settings (like how twitchy the tracker's own motion model should be) still needed to be chosen, and the honest way to choose them is to decide the rule for picking a winner *before* running the comparison, not after — otherwise it's trivially easy to accidentally pick whichever rule makes your favorite answer look best. And the final, once-only test on data nobody tuned against is protected by an actual piece of code that refuses to run without the right unlock conditions, not just a promise to be careful.

## Tiny worked numeric example
Two evaluation designs both report "fused wins by 5 percentage points." Design A tuned its shared settings by trying a few values and picking whichever made the *fused* number look best, then reported that same fused number as the final result. Design B pre-registered "we'll pick settings using the *average* score across all four configurations, not just fused" before running anything, then later found fused actually scored 87.2% against LiDAR-alone's 97.0% on the untouched test data — a real loss, reported as one. Design A's "fusion wins by 5 points" and Design B's honest "fusion actually loses by 10 points, but catches more real dangers" are not just different results — only one of them is a result you can trust, because only one of them was structurally prevented from being gamed, even unintentionally.

## Why it is designed this way (which past mistake it prevents — cite what-not-to-do.md/lessons)
`what-not-to-do.md` §7 states the rule this whole step exists to enforce: never tune anything to make fusion look better than it measures, and never let tuning and testing touch the same data. `lessons-from-v1-v2.md` item A.11 frames it even more directly — fusion's benefit is a claim to test, not an assumption to build the whole project around. It would have been very easy, after months of building a fusion pipeline, to unconsciously nudge the evaluation toward confirming that all that work paid off. The pre-declared criterion (DEC-7) and the code-level eval-split guard are both direct, mechanical defenses against that exact, very human failure mode — and the fact that fusion genuinely did *not* win on this dataset, with this design, is itself the strongest possible evidence those defenses were real and not just decorative.

## How to explain this in an interview (3 bullets)
- "I ran a real control experiment, not just a fusion pipeline: the exact same code, the exact same shared configuration, scored on data none of the tuning ever touched, comparing all four sensor configurations against each other honestly — and I pre-registered the rule for picking tuning values before running a single comparison, specifically so the rule couldn't be quietly chosen afterward to favor the result I might have wanted."
- "When my fused result came back worse than a single sensor on the primary metric, I didn't stop at reporting the number — I traced every one of the specific false alarms back to its cause, found that half of them came from one scene that was a textbook instance of a limitation I'd already identified and explicitly chosen not to solve in this version, and reported that honestly instead of either hiding it or quietly re-tuning to make it go away."
- "I built the 'don't touch the test set' rule as an actual piece of enforced code — a cryptographic hash of the frozen configuration has to match exactly, and an explicit flag has to be passed, or the program simply refuses to score the held-out data — with every attempt, successful or refused, permanently logged, rather than trusting a policy that depends on nobody making a mistake under deadline pressure."

## Common misunderstandings
- **"A negative result (fusion didn't win) means the project failed."** It means the *evaluation* succeeded — it answered a real question honestly instead of assuming the answer. A rigorous project that finds "our approach doesn't clearly help, and here's specifically why" is more valuable and more trustworthy than one that reports a suspiciously clean win with no real scrutiny behind it.
- **"If the eval split needs to be touched twice because of an infrastructure problem, the whole eval run is compromised."** Not automatically — what matters is *what actually happened* the first time. If nothing was genuinely scored (a crash before any ground-truth comparison occurred, confirmed via an audit log), completing a missing prerequisite and trying again is different from re-scoring to chase a better number, and the honest thing to do is state clearly which situation actually occurred, not assume the worse one by default.
- **"Investigating a surprising result and then still reporting it is a contradiction — if you investigated it, why not fix it?"** Not every finding is a bug to fix. Some are the honest, already-understood cost of a deliberate design choice made earlier in the project (like not solving crowd conflation in this version) — the right response to *those* findings is to trace them, confirm they're the already-known thing and not something new, and report that clearly, not to quietly patch around a documented, accepted limitation days before the project's own final checkpoint.
