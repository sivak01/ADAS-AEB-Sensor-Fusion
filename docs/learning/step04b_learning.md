# Step 04b — learning note

## The idea in plain language (≤ 8 sentences)
A radar bounces radio waves off a car and gets back several separate little "pings" — one off the bumper, one off a wheel well, one off a mirror — because a car isn't a single point, it's a collection of surfaces that each reflect a bit differently. If every ping went straight into the tracker as its own object, the tracker would think it's seeing several cars stacked on top of each other; clustering is simply "group the pings that are probably the same physical object back together" before anything downstream ever sees them. Radar has one superpower LiDAR and camera don't: every single ping also comes with an instantaneous velocity reading (Doppler), essentially for free, which in principle could tell you "closing at 8 m/s" the very first time the sensor ever sees an object, with no need to wait and watch its position move. This project deliberately switches that superpower off for its first, baseline radar result — not because it doesn't work, but because using a raw sensor-reported velocity directly in a safety-relevant TTC number is a known bad pattern (a different project's own written rule against it, and this project's own G17), so the honest thing to do is measure how well radar performs on position alone first, and treat Doppler as a clearly-labeled future upgrade, not something baked in by default. The other big radar fact of life: radar doesn't just see cars and people, it also sees things that never move — guard rails, road signs, manhole covers — and because those returns are real, physical, valid measurements, no upstream filter can perfectly promise they'll never look like a legitimate, closing hazard.

## Tiny worked numeric example
A real, physical construction barrier sits fixed at 18 metres ahead of the ego vehicle. The ego is driving toward it at 5 m/s and hasn't started braking. A minute of TTC math on this exact geometry: closing speed = (ego velocity − object velocity) · (direction to object) = (5 − 0) · 1 = 5 m/s (the object's own velocity is genuinely zero — it's a barrier). TTC = 18m ÷ 5m/s = **3.6 seconds**, comfortably inside this project's own GRADUAL threshold. Everything about that number is physically correct — the barrier really is 18m away, really is stationary, and the ego really is closing on it at 5 m/s. The only thing "wrong" is that this project's ground-truth answer key doesn't count a barrier as a scoreable hazard (it only scores vehicles and pedestrians), so a system that (correctly!) reacts to it gets marked as a "false brake" — which is exactly why this step's report states the false-brake number together with its root cause, not just the bare percentage.

## Why it is designed this way (which past mistake it prevents — cite the predecessor project's own lesson)
The predecessor project (V1) added its own extra filter on top of the sensor's built-in one, specifically to throw away stationary radar returns before they ever reached its tracker — a reasonable-sounding engineering choice that, if copied here without thinking, would have quietly answered this step's central question before it was even asked. This step's spec deliberately frames the ghost-return problem as a test of the rest of the pipeline (the corridor filter, the tracker, the debounce logic) rather than something to solve at the sensor-adapter layer, and says plainly: don't hack around it silently. Skipping V1's extra filter and reporting the resulting 1-false-brake-in-75 number, WITH its root cause traced all the way to a specific construction-zone barrier, is a direct, deliberate application of that instruction — it turns "radar sees ghosts sometimes" from a vague warning into one concrete, fully-explained example with a number attached.

## How to explain this in an interview (3 bullets)
- "I built the radar detection front end to cluster raw returns into one detection per real object, using a much wider clustering distance than LiDAR needs, because radar returns are sparser and spread out further per object — and I chose a minimum-cluster-size of just one point, since radar frequently only returns a single ping for a real object, so requiring more would silently throw away real detections."
- "I made a deliberate choice not to pre-filter stationary radar returns in the adapter itself, even though the predecessor project did — because this step was specifically designed to measure whether the rest of the pipeline's defenses (the path filter, the tracker, the debounce requirement) are enough on their own, and filtering upstream would have hidden that answer instead of measuring it."
- "When I found one false brake in the first real run, I didn't just report the percentage — I built a small diagnostic to trace it back to the exact detections that fed that specific track, confirmed they were flagged stationary by the sensor's own data with near-zero compensated velocity, and cross-referenced the scene's full annotation set to find the actual physical object (a construction barrier) causing it. That's the difference between reporting a metric and actually understanding what produced it."

## Common misunderstandings
- **"A false brake always means something is broken."** Not in this case — the traced example is a system correctly reacting to a real, physically-present stationary object with a genuinely shrinking distance. It's "wrong" only relative to a scoring rule that deliberately excludes non-vehicle/pedestrian objects from the ground truth, which is a reasonable evaluation choice, not a flaw in the object being detected.
- **"Since Doppler gives instant velocity, not using it is obviously worse."** It's a genuine, real trade-off, not free performance left on the table — using a sensor's own reported velocity directly in a safety calculation, without first independently verifying it, is exactly the kind of shortcut that has caused real problems in this project's own predecessor codebase and is called out by name in this project's own rules. Leaving it out by default is a conservative starting point that can be revisited as an explicitly-approved, clearly-labeled experiment later, not a permanent limitation.
- **"Radar's measured lateral accuracy being much tighter than the textbook 'radar is bad at angles' assumption must be a mistake."** It looked suspicious enough to investigate properly rather than accept — and held up under a real stress test (re-measuring after removing a large pool of irrelevant nearby detections gave an identical answer). The likely real explanation is that this measurement only looks at objects roughly straight ahead of the vehicle, where a radar's angular accuracy is at its best — a full 360-degree average would look considerably worse, and both numbers are true at once, describing different situations.
