# Step 01 — learning note

## The idea in plain language (≤ 8 sentences)
Real sensors don't politely take turns reporting at a shared, synchronized moment — a LiDAR spins around roughly 20 times a second, radars report roughly 13 times a second, and a camera fires roughly 12 times a second, all completely independently. Waiting for all of them to "line up" before reacting throws away exactly the freshness that makes fast reaction possible: if the radar has new information right now, a collision-avoidance system should be able to use it right now, not wait up to 80ms for the next synchronized tick. This step builds that: one merged, time-ordered stream of lightweight "something happened" events across every active sensor channel, where each event carries only pointers to its own data (never the actual sensor readings), so nothing expensive gets loaded until something downstream actually decides it needs to. The merge itself uses a classic efficient algorithm (heap-based merging of several already-sorted lists) rather than collecting everything and sorting it after the fact, which matters because this stream is meant to be consumed lazily, potentially over a live, unbounded feed later.

## Tiny worked numeric example
Within one nominal "sample" instant in the dataset, this step measured the real offsets between channels relative to LIDAR_TOP: RADAR_FRONT arrived 16.2 ms later, RADAR_FRONT_LEFT 4.7 ms later, RADAR_FRONT_RIGHT 8.1 ms *earlier*, and CAM_FRONT 35.5 ms earlier. That's a 51.7 ms spread (from −35.5 to +16.2) within what a naive design might treat as "the same instant." At highway speed (25 m/s ≈ 90 km/h), 51.7 ms of unaccounted-for timing difference corresponds to about 1.3 meters of real vehicle travel — treating these five readings as simultaneous would silently misplace an object (or the ego vehicle itself) by more than a meter before any other error even enters the picture.

## Why it is designed this way (which past mistake it prevents — cite what-not-to-do.md section)
This step is the direct infrastructure for what-not-to-do.md §2's core rule: "don't reuse one channel's timestamp for another channel" and "don't process only 2Hz samples/." Every `RawEvent` carries its *own* record's timestamp, ego_pose_token, and calibrated_sensor_token specifically so that borrowing another channel's values is structurally impossible downstream, not just discouraged by convention — the same discipline step02's `FrameContext.from_event()` enforces for transforms is enforced here for the event stream itself. The lazy design (events hold no sensor data) also sets up G3 correctly for the whole rest of the project: because loading is deferred to adapters, which arrive only after the tracker/TTC/debounce logic is already proven on synthetic data, no adapter can accidentally get built and tested against unproven downstream machinery.

## How to explain this in an interview (3 bullets)
- "I measured, not assumed, that different sensors on the same vehicle report at genuinely different real timestamps even within one 'synchronized' logical instant — up to about 52 milliseconds of spread in the data I checked — and designed the event stream so that difference is preserved and usable, not averaged away or ignored."
- "I merged multiple sensor streams using a heap-based merge rather than collecting everything into a list and sorting it afterward, which keeps the design lazy and streaming-friendly — a property that matters if this were ever pointed at a live feed instead of a fixed recorded dataset."
- "I kept the event objects themselves completely lightweight — pointers and timestamps only, no actual sensor data — specifically so that expensive work (loading a point cloud, decoding an image) only happens once something downstream has actually decided that event is worth acting on."

## Common misunderstandings
- **"If two sensor readings are labeled as being part of the same 'sample,' they were captured at the same real moment."** Measured directly in this step: up to ~52 ms of real spread within one nominal sample, which is exactly the situation `nuscenes-reference.md` and `what-not-to-do.md` warn about — the sample grouping is a bookkeeping convenience, not a claim about simultaneity.
- **"A native-rate rate (like 20 Hz for LiDAR) is a fixed metronome — events arrive at exactly evenly-spaced intervals."** The inter-arrival standard deviations measured here (3.65 ms for LiDAR up to 27.46 ms for camera) show this isn't the case; real hardware jitter is a real property of this data, not measurement noise from the analysis.
- **"Merging streams just means combining and sorting them."** A full sort assumes all the data is already collected; the heap-based merge used here works incrementally on already-sorted inputs and never needs the whole dataset in memory at once, which is a meaningfully different (and here, deliberately chosen) computational approach, not just a stylistic preference.
