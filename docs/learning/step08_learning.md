# Step 08 — learning note

## The idea in plain language (≤ 8 sentences)
A single moment's TTC reading can be wrong for all sorts of boring reasons — a sensor blip, a track that briefly matched the wrong object, ordinary noise — and a system that brakes hard the instant any one reading looks dangerous would be constantly, uncomfortably wrong. Real emergency-braking systems solve this cheaply: require the danger condition to hold for several real readings in a row before acting, not just one. This step builds exactly that "debounce" logic, plus the two-tier decision itself (a gentle warning tier, and a hard-braking tier for genuinely imminent danger), and makes the release symmetric — a tier that fired doesn't drop the instant things look safe again either, for the same reason it didn't fire on the first bad reading. A track quietly losing its lock (eviction) or briefly not having enough data to trust (NOT_ELIGIBLE) are both treated as distinctly different situations from "confidently safe," and both are recorded that way, not silently folded into "nothing's happening."

## Tiny worked numeric example
With a 3-update debounce requirement and updates arriving roughly every 100 milliseconds, a genuinely dangerous condition takes about 200 extra milliseconds (2 update-intervals) beyond the very first dangerous reading before the system actually acts — visible directly in this step's own timeline figure, where the action tier only switches to AEB two updates after the TTC trace first crosses below the 1.2-second cutoff. At a closing speed of 15 m/s, 200 milliseconds of added reaction delay costs about 3 meters of extra closing distance before the system reacts. That's the real, quantifiable price debounce charges for its false-alarm protection — and it's a good deal only because acting on a single bad frame would cost far more in false alarms than 3 meters costs in reaction time.

## Why it is designed this way (which past mistake it prevents — cite what-not-to-do.md section)
This step is a direct build-out of what-not-to-do.md §5's rule: "Don't act on a single frame's TTC. Require the danger condition to hold for N consecutive real updates... before triggering an action." The explicit rule against debouncing across different tracks (§4: resetting the counter the instant the critical object's identity changes) is the same short-memory design philosophy carried into the decision layer — rather than trying to prove two different tracked objects are "really" the same threat continuing, the system just treats an identity change as a fresh situation requiring its own fresh proof, which is cheap and conservative rather than clever and fragile. The strict separation between `NOT_ELIGIBLE` (no usable answer) and a confident `NONE` (safe) answer, carried through from step07 Part B, matters even more here: silently treating "I don't know yet" the same as "nothing's wrong" inside the actual action layer — the part of the system that decides whether to brake — would be the most consequential place for that confusion to happen.

## How to explain this in an interview (3 bullets)
- "I made the release rule symmetric with the trigger rule on purpose — a tier that fired needs the same number of consecutive safe readings to clear as it needed dangerous readings to set, which avoids a system that's twitchy about entering a cautious state but reluctant to leave it, or vice versa."
- "I found two real bugs through testing, not just wrote tests that happened to pass — one where a status number silently stayed at zero right up until the exact instant a decision fired (hiding real incremental progress from anything watching), and one where my own test's assumption about a synthetic scenario was wrong, not the code, which I only accepted after checking which one was actually mistaken."
- "The decision-tracking type this step returns is deliberately a superset of the project's core shared decision type, not a replacement for it — a data-modeling choice made specifically to avoid unilaterally changing an interface other, already-approved parts of the project might depend on."

## Common misunderstandings
- **"Debounce just means 'wait a bit before reacting.'"** It specifically means requiring several *real* updates of the *same* tracked object to agree — not simply waiting a fixed amount of time, and explicitly not counting prediction-only ticks (moments where the tracker guessed forward with no new real detection) toward the count.
- **"If a tier's condition briefly stops holding, it should drop back to NONE immediately."** The release rule requires the same number of consecutive safe readings the trigger rule required for danger readings — a single safe blip in the middle of a real emergency shouldn't cancel the response any more than a single dangerous blip should have started it.
- **"NOT_ELIGIBLE readings should reset the debounce counter, since they're not real evidence of danger."** They specifically do NOT reset anything (and also don't advance anything) — the whole point is that a track's data briefly being untrustworthy shouldn't erase a real, already-accumulating danger streak building around it.
