# Step 06 — learning note

## The idea in plain language (≤ 8 sentences)
A tracker's job is deceptively simple to state: look at a new detection, decide whether it belongs to something already being tracked or is something new, and update accordingly. The hard part is the "decide" step — a fixed-radius circle around a track's predicted position either fragments a fast-moving object (too tight) or lets in the wrong nearby object (too loose), so this tracker instead uses a radius that automatically scales with how *uncertain* the prediction currently is, combined with how noisy the new detection's own sensor is. When several detections arrive in the same batch (one sensor's whole scan, potentially several objects at once), the assignment of detections to tracks is solved as one global optimization problem — not "grab the nearest one for each track in turn" — so that a slightly-suboptimal early pick can't lock out a better overall pairing. Tracks are deliberately short-lived: they exist only long enough to get one trustworthy velocity estimate, then either keep getting refreshed by new matches or quietly expire if nothing matches for a short while. This project runs one shared tracker regardless of whether it's fed one sensor's detections or several sensors merged together — there's no separate "fusion" step bolted on afterward.

## Tiny worked numeric example
After two real position updates from a precise sensor, a track's predicted-position uncertainty shrinks to a variance of about 0.05 — tight. A new, much noisier detection (variance 2.25, a sensor roughly 7× less precise) then arrives 1.2 meters away. Using only the track's own tight uncertainty to judge this match gives a squared-distance score of 1.2² / 0.05 ≈ 29 — enormous, and the match gets wrongly rejected. Using the *combined* uncertainty (track's uncertainty plus the noisy sensor's own uncertainty, 0.05 + 2.25 = 2.30) gives 1.2² / 2.30 ≈ 0.63 — comfortably inside a normal acceptance threshold, and the match is correctly accepted. The entire dispute over "should this match" comes down to whether the incoming sensor's own noise is honestly included in the comparison — leaving it out doesn't just shift the answer a little, it can flip an obviously-correct match into a rejected one.

## Why it is designed this way (which past mistake it prevents — cite what-not-to-do.md section)
This step directly implements what-not-to-do.md §4's central rule — "the correct quantity is the innovation covariance S = P_pred + R, including the incoming detection's own measurement noise. Gating on P_pred alone produces a gate that collapses too tight right after a low-noise sensor's update — a real, found-and-fixed bug." The worked example above is that exact bug, reproduced and measured directly against this step's own tracker rather than assumed. what-not-to-do.md §1 also shapes what was deliberately left out: no per-sensor trackers merged afterward, no long eviction timers, no lifetime sensor-provenance bookkeeping — all explicitly named as MOT-shaped features this rescoped project doesn't need. The crowd-conflation test is a direct implementation of lessons-from-v1-v2.md item C.3's warning that a short memory limits *how long* a bad match survives, but does nothing to prevent the bad match from happening in the first place — and this step's own investigation found a more precise, more useful version of that warning than expected: the failure isn't just "two objects become one track," it can be "a track's identity gets silently reassigned to the wrong object while the total count looks fine."

## How to explain this in an interview (3 bullets)
- "I didn't just implement the correct gating formula — I reproduced the specific historical bug it fixes, measured with real numbers from my own tracker (a squared-distance score of 29 under the wrong method versus 0.6 under the correct one, against the same 9.2 threshold), so the fix isn't just theoretically justified, it's demonstrated."
- "When my first crowd-conflation test didn't reproduce the failure mode I expected, I didn't just soften the assertion and move on — I investigated why, realized my scenario didn't match the actual failure mechanism described in prior project lessons, redesigned it to match, and found something more specific and more useful than I was originally looking for: track count staying correct while track *identity* silently gets reassigned to the wrong object."
- "I used a genuinely global assignment algorithm (Hungarian/optimal bipartite matching) for associating a batch of detections to existing tracks, rather than a greedy nearest-first approach — this matters specifically when a batch has more than one detection, since a greedy method can lock in a locally-good but globally-worse set of pairings."

## Common misunderstandings
- **"A test that doesn't reproduce the expected failure means the failure doesn't exist."** My first crowd-conflation scenario "passed" cleanly with 2 separate tracks — which could easily be mistaken for "this isn't actually a problem." It wasn't that the problem doesn't exist; my synthetic scenario just didn't create the actual ambiguous situation (an object's *first* detection competing for an *already-established* track with no better alternative) that causes it.
- **"If the final track count matches the number of true objects, the tracking was correct."** The redesigned crowd-conflation test is a direct counterexample: 2 tracks remained for 2 objects, and yet one track's identity had been captured by the wrong object partway through — a count-only check would have completely missed this.
- **"An unmatched track not being updated this scan means its data is stale/lost."** It isn't — the tracker still reports a valid, correctly time-advanced position and uncertainty for it (via a non-mutating "peek" forward), it just doesn't permanently commit that forward-prediction into the track's own internal state unless something actually matched. The two are mathematically identical whenever the track does eventually get a real update.
