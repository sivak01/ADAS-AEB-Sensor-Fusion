# Step D0 — learning note

## The idea in plain language (≤ 8 sentences)
Before building anything that tries to detect or track objects, this step builds the answer key: for every 2 Hz annotated instant in every scene, which real objects were actually in the vehicle's path, how fast the gap to each was really closing, and what a correctly-behaving system should have done (brake hard, brake gently, or do nothing). This matters because it fixes the scoring rules *before* any results exist to tempt anyone into moving the goalposts — if you decide what "correct" means only after seeing how your system performed, the evaluation is worthless. It also forces an early, honest look at the data: this project's headline finding is that in nuScenes-mini, genuinely dangerous moments are rare (about 3.5% of in-path object-instants), which is a real fact about the dataset that shapes how much confidence the eventual results can carry. The step also has to decide, up front, which scenes get used for tuning thresholds and which get held out purely for the final, honest evaluation — and that split has to be locked in before anyone looks at how well any approach scores on it.

## Tiny worked numeric example
An object's bounding box is 4 meters long, centered 30 meters ahead of the ego vehicle. The nearest-surface rule (this project's chosen distance definition) says the reference point isn't the box's center — it's the box's near edge, 2 meters closer, at 28 meters. That's a 2-meter difference just from *which point on the object* you measure to, which at a 10 m/s closing speed is a 0.2-second difference in time-to-collision (28/10=2.8s vs. 30/10=3.0s) — small in this example, but for a bus or truck with an 8-10 meter length, the same effect could be a full second or more, which is the entire margin between a "gradual" and an "AEB" action tier in this project's thresholds.

## Why it is designed this way (which past mistake it prevents — cite what-not-to-do.md section)
Two specific things this step guards against, both named directly in `what-not-to-do.md`: §5's "don't use inconsistent distance definitions between the tracker's output and ground truth" — this step calls the exact same corridor and TTC functions the future tracking pipeline will call, not a separate hand-written copy, so the comparison is guaranteed apples-to-apples by construction rather than by careful bookkeeping. And §7's "don't tune thresholds using anything but the tuning split" and "don't treat a small number of danger events in nuScenes-mini as statistically solid" — this step exists specifically to lock in the tune/eval split *before* any tuning happens, and to state the thin-denominator problem in plain numbers (3 of 4 proposed eval-side danger cells fall below the minimum-count threshold) rather than let a future report quietly present a rate built on 5 events as if it were as solid as one built on 500.

## How to explain this in an interview (3 bullets)
- "I built the ground-truth evaluation table by calling the exact same corridor-membership and TTC functions the live pipeline uses, not a parallel reimplementation — this structurally prevents the class of bug where a subtle difference between 'how the system computes things' and 'how the evaluation computes things' makes a result look better or worse than it really is."
- "When I proposed how to split scenes into tuning and evaluation sets, I found that all of the most severe danger events were concentrated in a single scene, which meant no split could give both sides real representation of that category — instead of hiding that with a superficially balanced split, I stated the constraint explicitly and made a deliberate, justified choice about which side needed that data more."
- "I caught a bug in my own visualization, not just my data logic: an early version of a figure meant to show a dangerous scene rendered successfully but displayed nothing, because the object I wanted to show fell outside a fixed plotting window I'd chosen. It wasn't a crash, so it could have shipped as 'this scene has no danger events' — I caught it by checking the underlying numbers against what the figure showed, not by assuming a successful run meant a correct one."

## Common misunderstandings
- **"Distance to an object means distance to its center."** Under this project's DEC-1 (nearest-surface-to-ego), it specifically doesn't — the worked example above shows why that distinction has a real, non-trivial effect on the resulting TTC and action tier for a large vehicle.
- **"A script that runs without errors and produces a figure produced a *correct* figure."** The BEV-figure bug is a direct counterexample: the script ran cleanly, saved a valid PNG, and that PNG was simply wrong (missing the one thing it was supposed to show) — "it ran" and "it's right" are different claims, and only checking the actual rendered output (not just the exit code) catches the second one.
- **"If GT velocity can't always be computed cleanly, just drop those rows."** This step explicitly does the opposite — rows with invalid velocity are kept and counted (visible in every per-scene and overall total), just excluded from the TTC-based action label specifically, so the denominator of every rate stays honest about how much data actually went into it.
