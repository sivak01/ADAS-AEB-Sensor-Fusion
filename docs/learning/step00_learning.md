# Step 00 — learning note

## The idea in plain language (≤ 8 sentences)
Before writing a single line of pipeline logic, this step does three things: confirm the dataset on disk is actually what the design assumes (especially that per-sensor "sweeps" data exists, not just the slow 2Hz keyframes); create one file where every tunable constant lives, tagged as either `MEASURED` (backed by real data), `ASSUMED` (a reasonable guess, stated as such), or `PLACEHOLDER` (a stand-in a later step must replace); and define the small data shapes (a raw sensor event, a detection, a track snapshot, a TTC result, an action decision) that every later step will pass to each other. None of this is "real" pipeline code — no filtering, no tracking, no math — it's the scaffolding and the honesty bookkeeping everything else builds on. The `Param` idea specifically exists so nobody, including a future version of the author, can quietly forget which numbers were guessed versus which were actually measured from the data.

## Tiny worked numeric example
Take `CHI2_GATE`. Instead of writing `CHI2_GATE = 9.21` directly in the code, config.py computes it: `scipy.stats.chi2.ppf(0.99, df=2)`. If someone later decides a 95% confidence gate is more appropriate than 99%, they change one number (`0.99` → `0.95`) and the quantile recomputes itself correctly (`chi2.ppf(0.95, df=2) ≈ 5.99`) — there's no way for the "0.99 confidence" claim in the comment and the literal number actually used to drift apart, because there's only one number, computed, not two numbers that have to be kept in sync by hand.

## Why it is designed this way (which past mistake it prevents — cite what-not-to-do.md section)
This directly targets what-not-to-do.md §7: "Don't claim an R value is 'measured' when it's actually a literature-typical assumption." The predecessor project (V1) had a flat, un-tuned R value sitting unused next to correctly-tuned per-sensor values for a long time before anyone caught it (lessons-from-v1-v2.md item A.9) — a single shared config file with an explicit status field is the structural fix, not just a promise to "be careful." The `TunableOn` field also targets what-not-to-do.md §7's tuning-split discipline directly: a parameter marked `tunable_on="tune_split"` (like `SIGMA_A`, `DEBOUNCE_N`, `TTC_GRADUAL_S`) is flagged as something that must only ever be adjusted using the tuning scenes, never the held-out evaluation scenes — the field exists so that rule is visible in the code itself, not just in a document someone might not reread before tuning.

## How to explain this in an interview (3 bullets)
- "Every constant in the pipeline carries its own provenance — I never let a number claim to be 'measured' unless it actually was, and I made that a field in the data structure, not just a comment, so a test can enforce it."
- "I ran a dataset preflight before writing any pipeline code, specifically checking that the native-rate 'sweeps' data existed and had real files on disk — a shortcut a prior version of this project took (2Hz-only) had already been shown to distort filter tuning."
- "When I found the camera channels reporting an unusually round 10Hz instead of the commonly-cited ~12Hz, I didn't just accept it — I re-checked it per-scene and then at the raw-timestamp-gap level within one scene before deciding it was a real property of the data, not a bug in my own grouping logic."

## Common misunderstandings
- **"ASSUMED just means 'I didn't bother measuring it.'"** No — ASSUMED specifically means a literature-typical or reasoned starting value that the project is honest about not having measured yet, often because measuring it properly isn't safe to do yet (e.g. LiDAR/radar R couldn't be trusted-measured in the predecessor project because the measurement itself was corrupted by track fragmentation).
- **"PLACEHOLDER and ASSUMED are basically the same thing."** They're not: PLACEHOLDER specifically means "a named later step is going to replace this with a real measurement" (e.g. `MAX_VEL_STD_MPS` will be measured in step06) — it carries a forward-looking commitment that ASSUMED doesn't.
- **"If v2 already measured/tuned a similar constant, just reuse its number."** Not automatically — some of v2's numbers were retuned deliberately here (see `EVICTION_GAP_S` vs. v2's `MAX_MISSED_SECONDS`) because the underlying tradeoff (track lifetime) genuinely changed between the two projects' designs, not because the old number was wrong for its own context.
